# 临床时间窗口 v10.8：惰性精确盾（Lazy Exact Shield）与补测实验方案

> 文档状态：实验前方案（pre-run protocol）  
> 正式运行环境：仅 SSH 服务器 `RealDoctor240`  
> 适用范围：研究代码、冻结实验、统计分析、论文改写与 Port B 集成前验收  
> 核心原则：先证明等价性，再测速度；先冻结协议，再生成新的确认集；旧结果和旧实现均不覆盖。

## 0. 结论先行

方案在算法上可行，而且比当前“先把 6 个候选全部精确 rollout，再从安全候选中让网络选择”的 eager C4 更符合行为克隆的用途。

新方案的在线决策流程是：

1. 网络先对全部候选做廉价排序；
2. 只对排名第一的候选执行一次完整精确验证；
3. 若该候选安全，立即执行，不再计算其余候选；
4. 若不安全，再依次验证排名第二、第三……的候选；
5. 若所有候选都不安全，进入与旧 C4 完全相同的确定性 fallback。

只要网络排序不依赖精确 rollout 的输出，且候选集合、排序规则、安全谓词和 fallback 均保持一致，lazy C4 与旧 eager C4 应当逐动作完全一致。因此，lazy C4 理论上应当保留旧 C4 的手术时间和失血量，只减少未被选择候选的精确计算。

不过，“lazy C4 显著快于 C3”仍然只是待检验假设，不是算法定义自动保证的结论。C3 可以并行计算多个候选，而 lazy C4 每个宏动作仍至少需要一次完整尾部 rollout；在固定 CPU 预算下，两者差距可能小于直觉预期。正式改论文前必须通过本方案中的延迟 pilot 和新冻结确认实验。

本轮正式数字全部在 SSH 服务器上产生。本地仅用于编辑代码和查看结果，不承担 smoke test、计时或任何论文数字，以避免环境口径混杂。

## 1. 研究问题与预期角色

### 1.1 主要研究问题

本轮实验回答四个问题：

1. **语义等价性**：lazy C4 是否与旧 eager C4 在每个决策点选择完全相同的动作？
2. **安全性**：lazy C4 是否仍然保证每个最终执行的动作都经过完整精确验证，并维持零预算超限、零失败和零不变量破坏？
3. **计算效率**：lazy C4 是否在相同实验环境和明确的 CPU 资源口径下显著快于 C3 与 eager C4？
4. **折中位置**：lazy C4 的延迟是否稳定落在 C5 与 C3 之间，同时在尾部风险上优于无盾 C5？

### 1.2 期望形成的控制器谱系

| 控制器 | 选择依据 | 精确验证方式 | 预期角色 |
|---|---|---|---|
| C0 | 原始基线规则 | 按冻结基线定义 | 基线 |
| C2 | 既有消融控制器 | 按冻结定义 | 方法消融 |
| C3 | 对全部候选做完整精确 rollout，并按精确目标选优 | 全候选 | 高质量、强安全的精确教师 |
| C4-E | 网络排序，但预先精确计算全部候选 | eager，全候选 | 旧实现、等价性对照，不作为最终部署方案 |
| C4-L | 网络先排序，只按顺序验证到第一个安全候选 | lazy，通常一个候选 | 目标折中方案 |
| C5 | 网络直接选择 | 无精确盾 | 速度上界与尾部风险对照 |

在实验和代码中必须使用 `C4-E` 与 `C4-L` 区分新旧版本。只有全部验收门通过后，论文正文才可以把 `C4-L` 简称为 `C4`；旧版本应保留为 eager-shield ablation 或实现细节对照，不能从历史记录中消失。

### 1.3 非目标

本轮不做以下事情：

- 不重新训练行为克隆网络；
- 不改变候选动作集合、网络结构、特征或 checkpoint；
- 不放宽既有出血预算来制造通过结果；
- 不修改 v10.5、v10.6、v10.7 的冻结代码与结果；
- 不用旧 Replication 集上观察到的结果直接充当新方法的独立确认结论；
- 不在得知新确认集结果后调整安全阈值、排序 tie-break 或统计门槛。

## 2. 为什么 lazy C4 与 eager C4 可以等价

### 2.1 当前 eager C4 的本质

对一个状态 `s`，设候选集合为：

```text
A(s) = [a1, a2, ..., aK], K <= 6
```

网络给每个候选一个分数：

```text
q_i = model_score(s, a_i)
```

精确验证器对候选给出布尔结果：

```text
safe_i = ExactVerify(s, a_i, B_budget)
```

旧 eager C4 的选择可写成：

```text
argmax q_i, subject to safe_i = True
```

它先计算全部 `safe_i`，再从安全候选中选网络分数最高者。

### 2.2 新 lazy C4 的本质

先按完全相同的网络分数和 tie-break 排序：

```text
a_(1), a_(2), ..., a_(K)
```

然后从头逐个运行 `ExactVerify`，第一次得到 `True` 就停止并执行该候选。

```text
for a in ranked_candidates:
    result = ExactVerify(s, a, B_budget)
    if result.safe_exact:
        return a
return frozen_fallback(s)
```

### 2.3 等价性成立的必要条件

以下条件必须全部满足：

1. eager 与 lazy 使用完全相同、顺序稳定的候选集合；
2. 网络输入只依赖当前状态、候选动作及廉价特征，不依赖 `T_tail`、`B_total`、`safe_exact` 等精确验证输出；
3. 网络处于 `eval` 模式，无 dropout 或其他随机推理行为；
4. 分数相等时使用完全相同的确定性 tie-break；
5. `ExactVerify` 的 simulator、尾部策略、浮点容差和安全谓词完全相同；
6. 所有候选都不安全时，fallback 完全相同；
7. 候选验证不修改共享环境；每次验证都从同一状态的独立副本开始；
8. 并行与串行执行不会改变随机数流或模拟器结果。

当前 v10.7 C4 的网络特征不使用完整尾部 rollout 输出，因此具备改写成 lazy 形式的基础。但这仍须由单元测试和逐动作 hash 审计证明，不能只凭代码阅读下结论。

### 2.4 为什么相同改法不能直接用于 C3

C3 的目标不是“按已有排序找到第一个安全候选”，而是根据每个候选的完整精确结果比较 `T_total`，并在需要时比较 `B_total`。在没有额外的可证明上下界或最优性证书时，不计算剩余候选就无法知道当前候选是不是精确最优。

因此：

- 对 C4-L，完整 rollout 是**已选候选的安全验证**，通常一次即可停止；
- 对 C3，完整 rollout 是**产生决策排序本身所需的规划计算**，原则上需要全部候选；
- 把 C3 也改为“验证第一个安全候选”会改变 C3 的决策语义，使它成为另一个启发式算法，而不是原来的精确教师。

这一区分应在论文方法部分明确写出，避免把 C3 的全部规划成本误归因于 shield。

## 3. v10.8 算法契约

### 3.1 候选排序

候选排序必须复用旧 C4 的模型输入与打分：

```text
primary key:   model score，降序
secondary key: 冻结的 target 坐标字典序，升序
```

实现时不要依赖 Python 容器的偶然遍历顺序。排序后的候选 ID、原始候选索引和分数都写入诊断记录。

### 3.2 精确安全谓词

单个候选的精确验证继续使用 v10.7 冻结的完整尾部策略和安全合同：

```text
safe_exact = completion
             and failure_reason is None
             and B_total <= B_budget + 1e-9
```

`B_budget`、既有 margin（当前冻结值约为 `16.070543 mL`）及其计算来源全部沿用 v10.7 manifest，不因新方法或 C5 的结果而改变。正式实验前应从冻结文件读取并记录精确全精度值，文档中的近似值不能直接作为代码常量。

### 3.3 早停与 fallback

- 第一个通过精确验证的候选立即返回；
- 未验证候选保持 `unverified`，不得默认标记为安全或不安全；
- 若全部候选均被拒绝，调用旧 eager C4 的同一 fallback；
- fallback 若包含执行动作，该动作也必须满足冻结安全合同；
- 不允许把网络的风险预测当作放行依据；网络只决定验证顺序。

### 3.4 在线诊断字段

旧 eager 记录中的“全部安全候选数”和“所有候选的最坏出血量”在 lazy 在线路径中通常不可得。若为了保留这些字段继续计算其余候选，就会抵消加速。因此新在线记录至少改为：

- `candidate_count`
- `ranked_candidate_ids`
- `selected_candidate_id`
- `selected_rank`
- `verified_candidate_count`
- `rejected_candidate_count`
- `unverified_candidate_count`
- `selected_B_total`
- `selected_T_total`
- `selected_safe_exact`
- `fallback_used`
- `fallback_reason`
- `policy_forward_wall_s`
- `exact_verify_wall_s`
- `controller_wall_s`
- `process_cpu_s`

完整的全候选诊断只在 `audit_eager=True` 的离线审计模式生成，不得在论文的 lazy 延迟测量中开启。

## 6. 数据冻结与防止信息泄漏

### 6.1 旧 Replication 集的用途

旧的 256 场景 Replication 集已经被用于观察 eager C4、C3 和 C5，并参与了 lazy 设计讨论。因此它可以用于：

- 逐动作等价性审计；
- 查找实现 bug；
- 测试日志字段；
- 估算候选验证次数和运行时间；
- 决定是否值得进入新确认实验。

它不能单独支持“新 lazy C4 已被独立确认”的论文结论。

### 6.2 新冻结确认集

正式结论应使用一个新的 256 场景确认集。建议生成规则：

1. 初始随机种子固定为 `2026090301`；
2. 按 v10.7 相同的场景生成分布、尺寸条件与冻结流程生成；
3. 与所有历史 train/dev/tuning/validation/test/stress/replication/sensitivity 场景做 canonical scene hash 去重；
4. 若发现任何重合，完整记录冲突 seed，并将 seed 加 1 后重新生成整个集合，直到零重合；
5. 生成 `split_lazy_replication.json`、对应 baseline 与 manifest 后立即只读冻结；
6. 冻结完成后不得根据结果更换场景或 margin。

### 6.3 延迟子集

从新 256 场景确认集中，按冻结的 scene ID 排序后等距抽取 64 个场景，形成 `split_latency_64.json`。不能根据第一次测得的快慢挑选场景。

### 6.4 敏感性集合

从新确认集中按同样的预注册规则选 128 个 base scenes，施加与 v10.7.1 相同的五种扰动条件。扰动参数、随机数种子和 base-to-perturbed 映射在运行控制器前冻结。

## 7. 需要补测的实验

### 7.1 E0：代码、数据与环境取证

**目的**：确保新实验的全部输入可追溯。

**工作项**：

- 记录远端 commit、dirty status 与 patch；
- 校验旧 Replication、baseline、checkpoint 哈希；
- 解析实际论文环境，不使用系统 Python；
- 复核旧 C3/C4-E/C5 分片均为 256 场景且无缺失；
- 复核候选 `K <= 6`、安全谓词、margin、tail 策略及 tie-break；
- 建立 v10.8 新结果目录和 manifest schema。

**产物**：`audit/environment.json`、`audit/input_hashes.json`、`audit/code_provenance.txt`。

**通过标准**：所有输入哈希唯一且可解析，环境与预期一致，旧冻结结果未被修改。

### 7.2 E1：单元测试与契约测试

**必须覆盖**：

1. 排名第一安全：仅调用一次 `ExactVerify`；
2. 第一名不安全、第二名安全：调用两次且选择第二名；
3. 所有候选不安全：遍历全部候选并进入相同 fallback；
4. 分数完全相同：eager/lazy tie-break 一致；
5. `B_total` 恰在阈值、阈值上下 `1e-9` 附近：浮点边界一致；
6. completion 为 false：不能放行；
7. failure reason 非空：不能放行；
8. 验证过程中环境不可变，验证前后 state hash 一致；
9. 模型只前向一次，不得在每个候选验证后重复前向；
10. lazy 在线模式不偷偷计算未验证候选；
11. audit eager 模式可恢复全候选记录，但不得混入延迟实验；
12. 固定随机种子下重复两次，动作序列和日志 hash 一致。

**通过标准**：全部测试通过；任何一个动作语义测试失败都停止后续实验。

### 7.3 E2：8 场景远端 smoke test

**控制器**：C3、C4-E、C4-L、C5。

**检查项**：

- 每个场景正常完成；
- C4-E 与 C4-L 动作序列完全一致；
- C4-E 与 C4-L 的最终 `T_sim`、`B_total` 位级相同或在冻结数值容差内；
- C4-L 的每个已执行动作都有 `selected_safe_exact=True`；
- `verified_candidate_count` 合理，且存在真正的早停；
- 日志可被聚合脚本完整读取。

该阶段只排错，不产生论文数字。

### 7.4 E3：旧 Replication 256 场景回顾性等价审计

**目的**：利用已有数据最大限度检验实现，不把它当作独立确认。

**运行**：只新增运行 C4-L；复用已有 C4-E 分片做逐动作对照。若旧日志不足以重建逐动作排序，则 C4-E 也重新运行，但结果放在 `equivalence/`，不覆盖旧分片。

**逐场景断言**：

- `action_hash(C4-L) == action_hash(C4-E)`；
- 每一步 selected target、selected rank、fallback 标记相同；
- 最终 `T_sim`、`B_total`、completion、failure reason 相同；
- safety overrun 与 invariant violation 均相同；
- C4-L 的精确验证次数不大于 C4-E。

**当前可用于预估的数据**：旧 C4-E 共约 96,682 个宏动作，只有 79 次 shield intervention，分布于 41/256 个场景。若绝大多数场景的网络第一候选直接安全，则 C4-L 的平均验证数应接近 1。即使每次 intervention 都极端地验证其余 5 个候选，总验证数上界也约为 97,077，约 `1.0041` 次/宏动作。

这个估算非常有利，但不能替代实际计时，因为旧 eager 版本已经用 leaf pool 并行计算候选，wall time 不会按 6 倍线性下降。

**通过标准**：256/256 场景、所有宏动作完全等价；任何不等价都必须定位并修复，不能以“统计上差不多”放行。

### 7.5 E4：32 场景延迟 pilot 与 Stop/Go

**目的**：在投入完整新确认实验前，回答“lazy C4 是否真有机会快于充分并行的 C3”。

**场景**：从旧 Replication 按冻结 ID 等距抽取 32 个，仅用于工程决策。

**控制器**：C3、C4-E、C4-L、C5。

**两种资源口径**：

1. **历史连续性口径**：沿用 v10.7 的 `scene_workers=1`、`leaf_workers=3`；
2. **等 CPU 上限口径**：每个控制器允许相同的最大逻辑核预算。在 32 场景 pilot 上，对 C3/C4-E 预先比较 `leaf_workers ∈ {1, 2, 3, 6}`，按配对中位 wall time 选定一个配置并在新确认集前冻结；C4-L 即使只使用一个 verifier，也不能把空闲核另算成“免费”。worker 调优只能使用旧 pilot，不得在新确认集上重新挑配置。

需要同时记录 wall time 和 process CPU time：

- wall time 回答单病例等待多久；
- CPU time 回答实际消耗多少计算资源；
- throughput 另测，不得代替 latency。

**Go 条件**：

- C4-L 与 C4-E 动作完全等价；
- C4-L 相对 C3 的配对 wall time 中位数至少降低 20%；
- bootstrap 方向稳定，没有明显长尾倒退；
- C5 仍明显快于 C4-L；
- 每宏动作精确验证次数接近 1，且额外 Python 调度没有吞掉收益。

如果 C4-L 不能稳定快于 C3，先检查实现和资源公平性。若充分优化后仍不满足，不进入“C4 是速度—安全折中”的论文改写；保留结果作为负面工程发现。

这里存在真实失败风险：历史 v10.5 已证明全候选精确规划可以通过持久进程池获得较大并行收益。虽然它与 v10.7 不是同一 split/拓扑，不能直接比较数值，但它说明“C3 必然比 lazy C4 慢”并不成立。C4-L 的速度主张必须与调优后、资源上限相同的 C3 比，而不能只与一个人为较慢的串行 C3 比。

### 7.6 E5：生成并冻结新确认集

E4 通过后才执行。先生成 split、baseline、sensitivity base 和 latency subset，再输出 manifest。manifest 写入后才允许运行任何控制器。

**必须审计**：

- 场景数、尺寸分布、难度分布与既有协议一致；
- 与全部历史集合零 hash 重合；
- baseline 生成无失败；
- margin 和预算函数完全冻结；
- checkpoint 与模型配置不变。

### 7.7 E6：新 256 场景正式效果与安全确认

**控制器**：C0、C2、C3、C4-E、C4-L、C5。

**运行方式**：

- 每个 controller-scene 写独立原子 JSON；
- 支持断点续跑，但成功分片绝不覆盖；
- 可使用约 12 个 scene workers 提高吞吐；
- 正式效果指标使用 simulator 时间 `T_sim` 和失血量 `B_total`，不使用运行 wall time；
- C4-E 与 C4-L 必须在同一个新集合上都运行，以获得真正的独立等价确认。

**主要正确性终点**：

- C4-L 与 C4-E：256/256 action hash 完全相同；
- `T_sim` 与 `B_total` 配对差均为 0（在冻结容差内）；
- C4-L 零 completion failure、零 invariant violation、零预算超限；
- 每个最终执行动作均有精确验证证据。

**主要效果终点**：

- C4-L 相对 C0 的 `T_sim` 改善；
- C4-L 相对 C0 的 `B_total` 改善；
- C4-L 保留 C4-E 相对 C3 的既有质量折中；
- C5 的平均效果与尾部超限作为无盾对照，不预设它在新集合上一定出现超限。

**不得使用的表述**：

- 不能把 wall-clock 计算时间称为手术时间；
- 不能把均值失血改善写成“所有病例更安全”；
- 不能在 C5 出现尾部超限后临时放宽预算；
- 不能因 C4-L 与 C4-E 等价就省略新确认集上的 C4-E 运行。

### 7.8 E7：64 场景专用延迟基准

这是“C4-L 显著快于 C3、慢于 C5”的主要证据，不从并行吞吐作推断。

**设计**：

- 使用预先冻结的 64 场景 latency subset；
- `scene_workers=1`；
- 每个控制器、每个场景独立进程或明确重置状态；
- C3、C4-E、C4-L、C5 各运行 3 次；
- 每个 repetition 内采用平衡随机化的 controller 顺序；
- 固定 CPU affinity、线程数和最大 CPU 配额；
- 同时保存 wall time、CPU time、policy-forward time、exact-verify time、宏动作数和验证次数。

**预注册主要比较**：

1. C4-L vs C3：配对 `log(wall_time)` 差与速度比；
2. C4-L vs C4-E：早停带来的实现收益；
3. C4-L vs C5：精确安全验证的额外成本；
4. C3 vs C4-L 的 CPU time：避免并行实现掩盖总计算成本。

**“显著更快”门槛**：

- C4-L/C3 wall-time ratio 的配对 bootstrap 95% CI 上界小于 1；
- C4-L 的 p50 wall time 至少比 C3 低 20%；
- C4-L 的 p95 不高于 C3；
- 三次重复中结论方向一致；
- C5 p50 小于 C4-L p50，形成预期速度次序。

若只满足统计显著、但实际降幅不足 20%，论文应写“降低计算开销”，不要写“显著的临床级加速”或强折中结论。

### 7.9 E8：五条件敏感性补测

沿用 v10.7.1 的五类扰动定义和强度，不重新挑选有利扰动。建议至少运行 C0、C3、C4-E、C4-L、C5；若成本受限，C2 可不进入敏感性主表，但需在 manifest 中预先写明。

每个条件 128 个 base scenes，检查：

- C4-L 与 C4-E 在所有扰动下仍逐动作等价；
- 零超限、零失败和零不变量破坏是否维持；
- `verified_candidate_count` 是否在分布偏移下上升；
- C4-L 的 p95/p99 延迟是否因连续拒绝显著恶化；
- C5 的超限率、最大超限量和 Wilson 区间；
- C4-L 相对 C3/C0 的 `T_sim`、`B_total` 改善是否稳定。

敏感性实验的核心不是再次证明平均值，而是验证：当网络排序变差时，lazy shield 会增加验证次数并退化到更慢，但不能放弃安全性。

### 7.10 E9：最坏路径与合成回归

除随机场景外，必须构造能够触发以下路径的确定性测试：

- 第 1 名安全；
- 第 2、3、4、5、6 名才安全；
- 全部候选不安全；
- 候选不足 6 个；
- 相同分数；
- 恰好命中预算边界；
- completion/failure 异常；
- fallback 被触发；
- 重复调用不改变结果。

报告验证 rank=1…K 的单步耗时曲线，证明最坏情况下 lazy 退化为 eager 数量级，而不会产生未定义行为。

### 7.11 E10：Port B 桥接验收

研究 Gate 全通过后再集成。至少选择 3 个固定病例，每例重复 2 次：

- 旧 `learned_shielded` 与新 lazy ID 的动作序列一致；
- 输出 schema、前端展示和错误处理兼容；
- 两次 lazy 调用可复现；
- 选中动作均有精确验证记录；
- 新入口的端到端 wall time 低于旧 eager 入口；
- 旧算法 ID 仍可调用，以便回滚。

Port B 测试不代替研究冻结集，只验证产品桥接没有改变算法语义。

## 8. 统计分析计划

### 8.1 效果与安全

- 对 `T_sim`、`B_total` 报告 mean、SD、median、p5、p25、p75、p95、p99、min、max；
- 对成对控制器差值报告 wins/ties/losses；
- 使用场景级 paired bootstrap（10,000 次）给出均值差和中位数差的 95% CI；
- 超限率、失败率与不变量破坏率报告计数、比例和 Wilson 95% CI；
- 若比较两个配对的二分类超限结果，使用 McNemar exact test；事件数过少时只报告精确区间，不夸大显著性。

### 8.2 运行时间

- 主要分析单位为 scene，不把一个场景内的宏动作当作独立样本；
- 三次重复先对同一 scene-controller 取中位数，再做场景级配对统计；
- 报告 wall time 与 CPU time 的 p50/p95/max；
- 报告 `C4-L / C3`、`C4-L / C4-E`、`C4-L / C5` 的 paired ratio；
- 对 paired log-ratio 做 bootstrap 95% CI；
- 额外报告每宏动作平均验证数、rank 分布和早停率，用于解释加速来源。

### 8.3 指标角色

**主要指标**：

- C4-L 与 C4-E action hash 等价；
- C4-L 安全合同；
- C4-L vs C3 的专用延迟基准。

**次要指标**：

- C4-L vs C0 的 `T_sim` 与 `B_total`；
- C4-L vs C5 的安全—速度折中；
- 敏感性条件下的验证次数和尾延迟。

其余分析标为 exploratory，避免对大量指标只挑有利结果。

## 9. 验收门与失败后的处理

### Gate A：实现合同

- 所有单元测试通过；
- 验证不修改环境；
- 未验证候选没有伪造安全标签；
- fallback 与旧实现一致。

失败：停止，修代码后从 E1 重来。

### Gate B：旧集严格等价

- 256/256 场景 action hash 一致；
- 所有效果和安全输出一致；
- 实际验证次数显著下降。

失败：lazy 实现不能被称为 eager C4 的等价加速。

### Gate C：速度 pilot

- 在公平资源口径下，C4-L 相对 C3 中位延迟至少降低 20%；
- 方向稳定，且不出现不可接受的 p95 倒退。

失败：不生成新论文主张。可继续把 lazy 作为等价工程优化，但不能把它包装成 C3/C5 之间的显著折中点。

### Gate D：新确认集

- C4-L/C4-E 全动作等价；
- C4-L 零失败、零不变量破坏、零预算超限；
- 专用 latency benchmark 达到统计与实际意义门槛；
- C5 更快，但至少在确认或敏感性/最坏路径中表现出更高的尾部风险；若未观察到事件，只能报告置信区间，不能声称已证实更危险。

失败：保留旧 C4 结论或收缩论文主张，不得调预算、删场景或换统计口径补救。

### Gate E：产品桥接

- Port B 结果等价、接口兼容、重复可复现；
- 新入口端到端更快；
- 可回滚。

失败：研究结论可以保留，但不切换产品默认算法。

## 13. 论文改写条件与建议表述

只有 Gate D 通过后，才修改论文中的 C4 定义。建议逻辑为：

1. C3 是精确教师，为了比较候选的精确目标，需要计算全部候选尾部；
2. 行为克隆学习 C3 的候选偏好，主要用途是先给出高质量排序；
3. lazy exact shield 仅对准备执行的候选做精确验证，不安全才检查下一个；
4. 因而 C4-L 保持 eager C4 的安全决策语义，同时避免大多数无用候选 rollout；
5. C5 去掉精确验证，速度最高，但失去逐动作的硬安全保证；
6. C4-L 是 C3 的规划质量、C5 的推理速度与精确安全保证之间的工程折中。

可以使用的强结论必须与实测结果匹配，例如：

> The learned policy ranks candidate actions, while an exact verifier is invoked lazily only for the highest-ranked candidate that is about to be executed. This preserves action-level equivalence to the eager shield under the frozen safety contract, while avoiding most counterfactual tail rollouts.

在速度 Gate 尚未通过前，只能写“旨在降低计算成本”，不能写“显著快于 C3”。

旧 eager C4 应在方法附录或消融中交代：它是语义参考实现，用于验证 lazy 执行与完整安全过滤的一致性。这样既保留历史可追溯性，也不会把实现演进包装成从未存在过的原始设计。

```text

安全：C3 = C4-E = C4-L > C5
效果：C4-L = C4-E，并保持相对 C0 的时间与失血改善
```

若实测满足这一结构，lazy C4 可以合理地成为论文中的正式 C4，并把 eager C4 降为等价参考实现。

若 lazy C4 与 eager C4 等价但没有显著快过 C3，则它仍是有效的软件优化，却不足以承担“速度—安全折中创新点”的论文角色。此时应诚实收缩 C4 的主张，保留 C3 作为主要方法，不应继续通过放宽预算或弱化基线来制造预期排序。
